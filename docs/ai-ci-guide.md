# AI 执行测试与等待 CI 的操作指引

适用于受用户授权处理 Inkra 代码、MR 与合入的 AI。先按改动选择必要检查，
已有相同输入的通过证据可复用；不要为获得豁免额外跑一轮全量。
声明格式和发布规则见 [发布指南](releasing.md#explicit-local-test-confirmations)。

## 自动复用发布浏览器结果

- 发布流程会为每个浏览器检查计算实际输入指纹，并从可信的成功发布流程
  恢复历史结果。组件代码、相关文档示例、测试与辅助文件、共享样式、资源、
  依赖或运行环境变化时，受影响的检查仍需运行。仅 npm 版本或归档指纹变化，
  不再自动让所有模块失去复用资格。
- 这项复用由 CI 自动决定，不需要 AI 手工声明“未受影响”。检查摘要中
  本次执行、历史复用和本地确认的清单及来源；不能把复用描述成本次线上执行。
- 历史结果必须来自 `inkrajs/inkra` 的成功发布流程及当前源提交的祖先，
  文档工具提交也必须已经进入 `inkrajs/docs` main，并通过归档、运行身份和
  完整覆盖校验。复用保留原始线上通过时间，最长
  90 天，不会因再次复用而续期；本地确认不转成可复用的线上通过记录。
- 首次启用没有兼容基线时会正常测试并建立记录。缺失、过期、输入改变或
  无法确定依赖的检查不能凭旧结果免跑。不要为了“预热”额外派发 npm 发布。
- 确需刷新历史记录时，可在获授权的发布中使用 `force_browser=true`，
  重测扣除精确本地确认后的浏览器检查；不要为普通合入额外派发一次发布。
- 该机制针对发布浏览器回归；组件 MR 已有影响范围选择，本地组件声明仍按
  下述规则处理。基础构建、包身份、安装消费、水合和发布保护继续执行。

## 何时主动申报本地测试

1. 读取 PR **base 提交**中的 `.github/local-validation-policy.json`。
   核对当前 GitHub 账号的数字 ID、`allowed_groups`、`component_groups`
   及对应环境；PR 自己新增的授权不能用于本次豁免。
2. 确认当前工作树干净，记录实际已测试的完整 head SHA 与当前 PR base SHA。
   本地测试结束后新增的提交不能沿用旧声明。
3. 只选择与改动相关、实际完成且通过的组。以 `component:log` 为例，
   需覆盖策略中列出的 `log.test.mjs` 与 `log-refinement.test.mjs`，
   不能根据文件名前缀猜测范围。存在未完成的必需检查时不申报该组。
4. 记录实际命令、Node/React 版本、通过/失败/跳过数量及重要限制。
   仅填写实际测试覆盖的环境；在 React 19 上通过不代表 React 18 已验证，
   环境不匹配时保留相应线上检查。
5. 如果当前账号已授权、输入一致且证据完整，在创建或更新 MR 时主动加入
   **一个** `ci-local-validation` JSON 区块，填写精确组、环境、理由和证据链接。
   不必再询问一次是否使用已经符合条件的豁免。

证据可以放在用户已授权创建的 MR 描述或评论中；例如将完整测试记录放在
MR 的 Validation 小节，并以该 MR 的 `#validation` 链接作为证据。
发布前去除私人路径、凭证和无关业务数据。不要只写“AI 已验证”，也不要把
“本地确认、线上免跑”描述成“线上执行通过”。

用户授权处理仓库不等于允许冒用其他账号或给自己新增白名单。身份、组、
环境或报告不符合条件时，使用正常 CI 并简要说明原因。

## 查看结果与处理变更

- 查看 `Resolve trusted local tests` 和组件测试摘要，确认声明被接受，
  并确认**实际免跑的文件**与本地记录一致。声明存在不等于所有检查都会跳过；
  未匹配环境和其他组仍会执行。
- 本地测试失败先修复，保留失败原因。修复后重跑受影响检查，更新 head/base
  与证据；不要以豁免隐藏失败、延长超时碰运气或使用旧提交的结果。
- 源码、依赖、配置或候选包变化会影响证据适用性。浏览器声明还需记录
  实际测试的候选包 SHA-256；文档端流程见
  [文档仓库指引](https://github.com/inkrajs/docs/blob/main/docs/ai-ci-guide.md)。
- MR 描述更新会触发 edited 检查。集中一次更新声明，确认新的检查已接手，
  避免反复编辑造成检查取消、重复启动。

## 何时等待、何时结束

- 用户要求合入时，等待当前提交真正必需的检查与合入门禁，通过后再合入。
  构建、包身份、安装消费及发布保护不由模块声明免除。
- 监控使用带间隔的状态等待；状态未变时降低轮询频率，不重复启动本地构建
  或发布验证来“确认还在跑”。同一输入的临时失败只重试失败任务。
- 合入后同步本地 main（例如 `git merge --ff-only origin/main`），报告合并
  结果并结束。用户没有要求发布、部署或合入后验证时，不等待这些后续流程，
  不额外派发发布、全量浏览器测试或基准运行。
- 正常 CI 尚未结束、失败或未接受声明时，应准确报告实际状态；不能提前
  声称完成。需要等待的门禁不能因“节省时间”被忽略。

## 给后续 AI 的可复用提示词

> 完成改动后，按实际影响范围运行必要的本地检查。读取 MR base 的本地测试
> 授权策略；如果当前账号获授权，且当前提交、环境、测试组和报告均符合要求，
> 主动在 MR 描述中填写 ci-local-validation 声明，使用真实结果减少重复线上测试。
> 查看 CI 自动历史复用的清单与原始通过来源，核对接受的本地声明及实际免跑
> 清单；不要为获取豁免重跑全套，也不要手写或修改历史基线。保留其他必需检查。
> 修复或新增提交后更新
> 对应测试与声明，不用旧证据覆盖新输入。等待当前提交的合入门禁并完成合入，
> 同步本地 main 后结束，除非用户另行要求发布、部署或后续验证。
